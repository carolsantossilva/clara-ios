# ADR 0001 — Modularization with a local SPM package and an XcodeGen project

**Status:** accepted

## Context

The app has three features, platform services and a design system. In a large app, each feature's code needs to compile and be tested in isolation, the dependency graph needs to be explicit, and the `.xcodeproj` must not be a source of merge conflicts.

## Decision

- One local SPM package (`Packages/ClaraKit`) with one target per module. Features depend on `ClaraCore` (models + protocols) and on services; **no feature depends on another**.
- The app is the *composition root*: only it knows the concrete implementations (database, HTTP, AI) and injects them.
- The `.xcodeproj` is generated by XcodeGen from `project.yml` and stays out of git.
- Shared test doubles live in `ClaraTestSupport`, a common target used only by tests.

## Alternatives considered

- **CocoaPods:** in maintenance mode; adds `Podfile.lock`, a workspace and build scripts. SPM is built into Xcode. In an app that already uses Pods, the migration would be gradual: new modules in SPM living alongside the old pods.
- **Tuist:** more powerful (module caching, graph, templates). It is the natural next step if the number of modules grows; XcodeGen was chosen for being simpler at the current size.
- **Bazel/Buck:** remote builds and distributed caching pay off with hundreds of modules and many developers; at this size, the cost of maintaining the rules does not.

## Consequences

- Smaller incremental builds: changing `RecordsFeature` does not recompile `TodayFeature`.
- The compiler prevents forbidden dependencies (a feature importing another does not compile).
- Cost: more `public` declarations and explicit inits at module boundaries.
